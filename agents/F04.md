## 3. Existing Automated Tests

Current TC01–TC07 package structure (smoke test remains in the base package):

```text
src/test/java/com/bgr/qa/
├── WebsiteSmokeTest.java
├── helpers/
│   └── UiAccountHelper.java
└── voting/
    ├── GuestVotingTest.java       # TC01, TC02
    ├── VotingEligibilityTest.java # TC03, TC04
    └── RepeatVotingTest.java      # TC05, TC06, TC07
```

Each test method uses an independent browser session. `VotingEligibilityTest`
creates its driver and explicit wait in `@BeforeMethod`; each scenario prepares
its own account at the start of its test method. Always-run cleanup closes the
browser even if preparation fails. No method depends on another test or its order.


### WebsiteSmokeTest.java

Purpose:
- Open the homepage.
- Check that the browser page title is not empty.

This is a basic smoke check, not comprehensive website availability verification.

### voting/GuestVotingTest.java

Automates:

**VOTE-TC01 — Guest cannot vote**
- Open a car model page as a guest.
- Verify the guest voting restriction.
- Verify that the Vote! button is absent.

**VOTE-TC02 — Guest cannot comment**
- Open a car model page as a guest.
- Verify that the comment input is unavailable.

### voting/VotingEligibilityTest.java

Automates:

**VOTE-TC03 — First eligible vote**
- Prepare a newly registered and authenticated account.
- Open the car voting page.
- Verify that the Vote! button is visible and enabled.
- Verify that the page does not already show a successful vote.
- Submit exactly one vote.
- Verify the success message.
- Verify the Vote! button disappears.

This test verifies visible UI behaviour only. It does not prove server-side vote uniqueness.

**VOTE-TC04 — Login without manual refresh**
- Registers a fresh account without logging in, verifies guest restrictions on the car page,
  then logs in through the navigation form.
- Verifies the same car URL and an enabled Vote! button without refreshing or voting.

### voting/RepeatVotingTest.java

**VOTE-TC05 — Second vote without refresh**
- Prepares its own fresh authenticated account and submits exactly one vote.
- Verifies success and removal of Vote! without refreshing, navigating or logging out.
- Does not attempt a second vote or claim server-side duplicate-vote enforcement.

**VOTE-TC06 — Repeat-vote restriction after refresh**
- Creates a fresh authenticated account with `UiAccountHelper.registerAndLogin`.
- Waits for an available Vote! button, submits exactly one vote, and verifies success.
- Refreshes the car page exactly once and waits for authentication and voting content
  to load before checking absence; an empty loading page cannot pass the restriction check.
- Verifies the same car URL and absence of Vote! after refresh. No second vote is attempted.
- Uses explicit waits and always-run browser cleanup. Verifies UI restriction only,
  not server-side duplicate-vote enforcement. Both methods run independently with fresh accounts.

### helpers/UiAccountHelper.java

Public helper operations:

- `register(driver, wait)` returns an immutable `Credentials` record without logging in.
- `login(driver, wait, credentials)` signs in on the current page without navigation.
- `registerAndLogin(driver, wait)` preserves the convenience wrapper.

The helper class, record and operations are public for use from `com.bgr.qa.voting`.
The record redacts its `toString()` output.

Current implementation:
- Generates a unique username using UUID.
- Generates a password using UUID plus required character types.
- Opens the registration page.
- Completes registration through the public UI.
- Verifies the registration success message.
- Logs in using the navigation login form.
- Verifies authenticated state by waiting for the Logout link.

The helper uses the WebDriver and WebDriverWait supplied by the calling test.

Do not print or persist generated credentials.

## 5. Test Data and State Management

Voting and registration modify persistent data in the public demo application.

Rules:
- Use a fresh eligible account for first-vote scenarios.
- Do not assume a fresh browser means a fresh account.
- Do not reuse an account that has already voted when eligibility is required.
- Do not automatically retry uncertain registration or vote submissions.
- Keep individual tests independent where practical.
- Use explicit waits for UI state transitions.
- Close browser sessions after execution.
- Do not assume closing Chrome removes accounts or votes.

Avoid unnecessary repeated executions of tests that create accounts or submit votes.

## 7. VOTE-TC04 — Approved Scenario (Implemented)

**Objective:** Verify that the voting UI updates after login without requiring a manual refresh.

### Preconditions

- A fresh eligible account exists.
- The browser is logged out.
- The car voting page is accessible.

### Test procedure

1. Prepare the account before the test action.
2. Establish a guest session.
3. Open the car model page.
4. Verify the guest voting restriction.
5. Enter the prepared account credentials through the top navigation.
6. Click Login.
7. Do not manually refresh or reopen the car page.
8. Verify the browser remains on the same car model page.
9. Verify that the Vote! button becomes available.

### Expected result

The user remains on the same car page and the voting UI changes from guest-restricted to authenticated and eligible without a test-triggered refresh or navigation.

Do not submit a vote in VOTE-TC04.

### Completed helper refactor

Implemented for TC04:

- Separate account registration and login into reusable operations.
- Return generated credentials using a small immutable object or record.
- Preserve the existing `registerAndLogin(driver, wait)` method so TC03 remains compatible.
- Preserve existing locator behaviour.
- Verify the refactor before adding TC04.

The helper refactor and TC04 implementation should be separate logical changes.
